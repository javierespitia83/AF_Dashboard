# DATA_CONTRACT.md

The sprint page reads `sprints.json` when valid and fetches only the selected sprint snapshot referenced by it; there is no fallback, so a missing or invalid manifest shows a clear error. The backlog page reads `backlog.json`. The Quality Intake page reads `quality-intake.json`. The active sprint snapshot (`snapshots/sprint-<id>.json`) and `backlog.json` are generated by `05_Automation/export_dashboard_snapshots.py` from the tracker `03_Tracker/daily_tracker.xlsx` (in `03_Team_Enablement/` until 2026-10-29) (`Daily` and `Backlog Prioritized`); `quality-intake.json` is generated from `Sprint Metrics` and `Quality Intake Detail`. The exporter lives outside this repo (`$AF_SNAPLOGIC_ROOT/05_Automation/`, see `README.md` "Paths"); `sprints.json` is updated at sprint rotation. Exporter behavior is documented in `$AF_SNAPLOGIC_ROOT/06_Skills/af-dashboard-snapshot-export.md`; schemas (JSON Schema 2020-12) are in `schema/`, and fixtures are in `fixtures/`. If this file and the exporter disagree, the exporter and its skill are the source of truth: fix this file. If this file and `SPEC.md` disagree, this file wins on data meaning and calculations and `SPEC.md` on presentation and behaviour (precedence rule at the top of `SPEC.md`, D80).

There are four kinds of data file: the manifest `sprints.json`, sprint snapshots `snapshots/sprint-<id>.json` (one per sprint, active or closed), `backlog.json` and `quality-intake.json`.

The top bar labels exported data as a snapshot and shows its export time when available. The adjacent Jira dashboard link is opened only when clicked; loading this app does not make a Jira request. The Jira dashboard is the user's route to current Jira data.

## Sprint rotation and manifest (`sprints.json`)

The manifest is the allowlist and index for sprint snapshots. It contains `current` (the active sprint id) and `sprints` (one entry per available sprint). Each entry requires integer `id`, `name`, ISO `startDate` and `endDate`, `state` (`active` or `closed`), and `file`; optional `note` explains snapshot caveats. `file` must be exactly `snapshots/sprint-<digits>.json` (D74), so it can never be absolute, a URL, or leave the `snapshots/` folder. Exactly one entry is active, and its id must equal `current`; ids are unique. The UI validates these rules before rendering the selector and ignores keys it does not know (so a new exporter field cannot take the page down); the schema `schema/sprints.schema.json` stays strict, so producers must still add new keys to it. The snapshot a manifest entry names must carry a `sprint` object whose `id`, `startDate` and `endDate` equal the entry; otherwise the page refuses it with a message saying so.

At rotation, **freeze the closing sprint into `snapshots/sprint-<id>.json` before the tracker's `Daily` tab rolls over**, then update the manifest with the newly active sprint entry and the closed snapshot entry. The exporter/rotation workflow will generate these files later; it is not implemented in this repo. Since 2026-10-26 the exporter writes the active sprint straight to `snapshots/sprint-<id>.json` (the `file` of its manifest entry) and there is no root `sprint.json` any more (D73), so rotation no longer copies or renames a file: add the new sprint to `sprints.json` as `active`, point `current` at it and mark the closed one `closed`. Which sprint is active is decided only by the manifest (state taken from Jira), never by a flag inside the snapshot. `fixtures/sprints.json` is a manifest fixture, not a live data source.

The Sprint selector defaults to `current`. A `?sprint=<id>` URL parameter is resolved only against manifest entries; it never becomes a path directly. Changing selection uses `history.replaceState`, resets sprint filters, and loads one selected snapshot; snapshots already fetched remain cached in memory. The backlog page is independent and continues to read only `backlog.json`.

## Quality intake history (`quality-intake.json`)

The Quality Intake page reads only this file. The exporter builds it from `Sprint Metrics` and `Quality Intake Detail`; it does not query Jira. Each entry represents one sprint and carries its own tracker-defined intake window, which can differ from the sprint's Jira start and end dates. `windowStart` and `windowEnd` are inclusive local calendar dates in America/Los_Angeles. `weekdays` is the weekday denominator already recorded in Sprint Metrics; the dashboard does not recalculate it. A source's rate is `count × 10 ÷ weekdays`, rounded to two decimals in JSON and one decimal for display. A missing count, missing weekday value, or zero weekdays produces `null` for that rate; missing values display as `n/a`.

`counts.pswat` includes issues from the PSWAT project regardless of issue type. `counts.appBugs` includes APP project issues whose Jira issue type is exactly `Bug`. These are intake counts, not defect escape rate. `partial: true` means the intake window is still partial; the current active sprint is shown with a partial badge.

`tickets` contains the source, Jira key, summary, type, status, created date, and Jira URL for click-through. The exporter reconciles detail-row counts by sprint and source against populated `PSWAT Created` and `APP Bugs Created` cells; any mismatch stops export before writing. A blank metric stays null and displays `n/a` instead of failing. Ticket keys and summaries are intentionally included in the published `quality-intake.json`; Carlos accepted this privacy exposure for now. Keep this detail limited to the requested intake page and do not add it to sprint or backlog snapshots.

## 1. File shape (sprint snapshots and `backlog.json`)

```json
{ "refreshedAt": "YYYY-MM-DD", "exportedAt": "YYYY-MM-DDTHH:MM:SS±HH:MM", "source": "<workbook · sheet>", "tickets": [ ... ] }
```

- `refreshedAt` is the local calendar date used by date-based calculations; keep it as `YYYY-MM-DD`.
- `exportedAt` is an optional RFC 3339 timestamp with the exporter machine's UTC offset. Convert it to the viewing browser's local timezone before displaying its date, time and UTC offset; older snapshots without it show `refreshedAt` only.
- `tickets` may be an empty array (show an empty state, not an error).
- Order of `tickets` is the sheet's row order. Preserve it unless a feature says otherwise.
- Every sprint, active or closed, is a file `snapshots/sprint-<id>.json` listed in `sprints.json`; the exporter rewrites the active one, closed ones are frozen. `backlog.json` and `quality-intake.json` hold the latest snapshot.

## 2a. `sprint` object (sprint snapshots only) and the new ticket fields

Every sprint snapshot has a top-level `sprint` object, read from the sprint's row in the tracker's `Sprint Metrics` tab:

| Field | Type | Meaning |
|---|---|---|
| `id` | integer | Jira sprint id (e.g. `12119`) |
| `name` | string or null | e.g. `APP Sprint 10-09-2026` |
| `startDate` | string (date) or null | `YYYY-MM-DD`, America/Los_Angeles |
| `endDate` | string (date) or null | `YYYY-MM-DD`; changes if the sprint is extended |
| `state` | `active` or `closed`, optional | Present in some frozen snapshots of closed sprints (for example `sprint-12119`), absent in others (`sprint-12176`) and in the active sprint's snapshot. The app does not read it: the manifest decides which sprint is active |
| `completeDate` | string (date) or null, optional | `YYYY-MM-DD` the sprint was completed in Jira; like `state`, only in some frozen snapshots |
| `carriedOver` | object or null | `{ "count": int or null, "percent": number 0 to 100 or null, "storyPoints": int or null, "ticketKeys"?: string[] }` |
| `removed` | array, null or absent | **Optional (D52).** Tickets that were in the sprint and left it (moved to a later sprint or the backlog). One entry per ticket: `ticket` (key), `removedDate` (`YYYY-MM-DD`, required), and optional `points`, `addedDate` (when it entered the sprint; absent means from the start), `summary`, `status` (at removal), `type`, `owner`, `tester`, `classifications`, `fixVersion`, `parent`, and `note` (string or null: a free-text caveat about the record, for example that it was reconstructed by hand after the sprint closed, as in `sprint-12119`; the app does not display it, D75). Must come from the Jira changelog (Sprint field); the UI never infers it. `type` is exact Jira issue type, nullable and optional for legacy removal rows. Absent or `null` = not available (the burndown footnote says removals are not reflected); `[]` = nothing was removed. |

Rules the UI must respect:
- **Self-tested rule (R001-17, R001-18, 2026-10-30).** A ticket is self-tested when `classifications`, split on `"; "`, contains the exact value `Dev to Test` or the exact value `QA to Test`, or when `tester` equals `owner` (both present). In the sprint Ticket detail table the column `Self-tested` appears immediately after `Tester` and shows, in this precedence, `Dev to Test`, `QA to Test`, `Same person` (tester = assignee, neither classification) or `—` (another person tests, or there is no tester). The classification wins even when another person is the tester (for example 13 tickets in sprint 4697). The `No tester` KPI, the attention panel's Missing line and the grid's `Unassigned` column use the same exact-value rule. Values such as `Dev to Testing` do not count.
- **`carriedOver` is a passthrough.** It is read straight from the `Carried Over #`, `Carried Over %` and `Carried Over Story Points` columns of `Sprint Metrics`. **Never recalculate it from the ticket list**: the comparison between sprints is only possible at rotation time, and only the tracker captures it.
- **`carriedOver: null` means "not calculated yet"** (all three source cells empty, e.g. a sprint that has just rotated). It is not "zero carried over". The UI must show it as not calculated, never as 0. A zero count arrives as `{ "count": 0, ... }`.
- `carriedOver.ticketKeys` is optional and, when present, identifies which current sprint tickets are included in the aggregate. The KPI can filter the lower section by these keys. Without it, the aggregate remains visible but the ticket-level set cannot be shown.
- **`addedDate` is the tracker's `Added to Sprint` date.** Since 2026-10-05, the tracker workflow records the Jira changelog date for every ticket (a ticket without a Sprint-field entry uses its Created date as the fallback). The exporter strips the retired trailing `*` marker, so older snapshots may contain dates whose origin cannot be identified from JSON alone. The current UI treats the exported date as the tracker's date; do not infer or recreate an approximation marker from other fields. Dates are compared as calendar days: a value that is not a `YYYY-MM-DD` date never counts as added mid-sprint and is treated as in scope from day one by the burndown. The detail table does not show it.
- **`doneDate` and `cycleTime`** are only populated for Done tickets; `null` elsewhere is by design (the metric does not apply), not missing data. A Done ticket without a `doneDate` is possible and is counted separately in the burndown footnote.
- **`removed` is optional** and is the only source of removals: tickets that left the sprint are not in `tickets`, so without it they cannot be known. Entries without a valid `removedDate` are ignored. Removed entries respond to the sprint filters through the fields they carry (`status`, `owner`, `tester`, `fixVersion`, `parent`; a missing owner or tester counts as `Unassigned`, a missing fix version or parent as `(none)`).
- The `sprint` object is required in practice: a snapshot without it (or with an id or dates that differ from its manifest entry) is refused with an error, so the sprint-dependent tiles always have sprint dates. The former "no sprint data" and "no sprint dates" tile messages were removed (D77).

## 4. Null, empty and numeric rules

- Blank or missing source values arrive as JSON `null` (never `""`, never `"None"`). The UI should still treat an empty string defensively as null.
- `points` is a JSON number or `null`, never a string. The UI must not parse numeric strings.
- Display `—` for any missing text, points or days value. Do not show `null`, `undefined`, `NaN` or blank cells.
- Calculations treat missing `points` as 0. The `—` is display only.
- Never invent a value. Ticket keys and names are shown exactly as exported (no trimming of meaning, no case changes, no reformatting).
- An unassigned owner would normally arrive as `null` (no sprint ticket lacks an owner in the current data, and none carries the literal text `"Unassigned"`), but the fixture (APP-3053) uses the literal string `"Unassigned"`. The UI treats both as the same group `Unassigned`, so either form is safe.

## 5. Status handling (sprint)

The exporter preserves the original status. The UI maps it for display:

| Original `status` | Display group (bucket) |
|---|---|
| `To Do`, `Open` | **To Do/Open** |
| `In Progress` | **In Progress** |
| `In Review` | **In Review** |
| `Done` | **Done** |
| anything else, or null | **Other** (shown as its own group; never dropped) |

Bucket order everywhere: To Do/Open, In Progress, In Review, Done, Other. Show the Other bucket only when it has tickets; when shown it must appear in totals. The detail table shows the original status text.

## 6. Calculations and filtering

"Work items" means number of tickets. Every number on the page is computed over a **filtered set**: the tickets that match the active cross-filters (see `SPEC.md` §5).

**Filter dimension values** (the exact key a click selects). Fix version and Parent (sprint) and Epic (backlog) are no longer dimensions since 2026-10-30 (R001-19, D87): the search (§7) matches them instead.

| Page | Dimension | Value of a ticket |
|---|---|---|
| Sprint | Status | its bucket: `To Do/Open`, `In Progress`, `In Review`, `Done`, `Other` (§5) |
| Sprint | Type | exact `type` value, or `—` when null |
| Sprint | Assignee | `owner` (null, blank or `Unassigned` → `Unassigned`) |
| Sprint | Tester | tester group (R001-17, R001-18): `Self-tested` when `classifications` has the exact `Dev to Test` or `QA to Test` and `tester` is null, blank or `Unassigned`, or when `tester` equals `owner`; `Unassigned` when there is no tester and the ticket is not self-tested; otherwise `tester` (also for a ticket with one of those classifications that another person tests) |
| Backlog | DoR | `dor` as exported, or `—` when null |
| Backlog | Priority | `priority`, or `—` when null |
| Backlog | Type | `type`, or `—` when null |
| Backlog | Age | bucket of `days`: `0–30`, `31–90`, `91–180`, `181–365`, `366+`, or `No value` when null |

**Combining:** values inside one dimension are OR; different dimensions are AND; the text search of either page (§7) is AND with all of them. A tile for dimension D is computed over the set filtered by every dimension **except D** (a matrix tile except both of its dimensions); KPI tiles, Needs attention today and the ticket table use the set filtered by everything (the KPI filters scope only the lower section).

**Sprint Ticket detail sorting:** text columns use natural alphabetical/numeric ordering; Story points and Days in status (`statusAging`) sort numerically. Missing values sort last in ascending order and first in descending order, making unassigned fields such as Fix version easy to bring to the top. Sorting only reorders the visible filtered rows; tracker order is the default.

**Sprint metrics (over the relevant set):**

| Metric | Definition |
|---|---|
| Work items | count of tickets |
| Story points | sum of `points`, missing = 0 |
| Done % | Done-bucket story points ÷ story points, as a whole percent; `—` when story points is 0 |
| No tester & not self-tested | count of tickets whose `tester` is null, blank, missing, or `Unassigned` and whose `classifications`, split on `"; "`, includes neither the exact value `Dev to Test` nor the exact value `QA to Test` (R001-18; label until 2026-10-30: No tester & Not Dev to Test) |
| Avg cycle time | mean of `cycleTime` over tickets with bucket `Done` and a non-null `cycleTime`; shown with at most one decimal; `—` when there are none |
| Added mid-sprint | tickets whose `addedDate` is a valid `YYYY-MM-DD` date later than `startDate` + the threshold, compared as calendar days; the threshold is `AF.config.midSprintThresholdDays` in `dashboard.js`, 1 day (D72); reports the count and the points |
| Carried over | `sprint.carriedOver` as exported (not filtered, not recalculated): count, percent, story points |
| Tickets by status | per bucket: `N W.I \| P SP`; bar length = bucket work items ÷ tile work items; Total row = tile totals |
| Tickets by type | exact type value (null grouped as `—`): count and sum of points as `N W.I \| P SP`; rows sort by work item count descending then type; bar length = share of work items; Total row = tile totals. The tile excludes its own Type filter, and clicking a row filters by that exact type value. |
| Needs attention today | tickets not in the Done bucket with at least one reason: Long-running (`status` In Progress or In Review and `statusAging` ≥ `AF.config.timeInStatusThresholdDays`), Carried over (key in `sprint.carriedOver.ticketKeys`), Blocked by `<key>` (each `<key> (is blocked by)` in `linkedWorkItems` whose ticket is not Done in this snapshot; a key not in the snapshot counts as open), Blocker recorded (`blocker` not blank; the text is never shown). Sorted by `statusAging` descending (null last), then key in natural order. Missing line over the filtered set: No tester & not self-tested count, tickets with null or blank `fixVersion`, tickets whose `points` is not a number. Shows no `owner`, `tester` or `blocker` text. |
| Assignee x tester | cell = count of tickets with that assignee group and that tester group (Tester row of the dimension table above); rows and columns sorted by total work items descending, `Self-tested` then `Unassigned` columns last; the `Unassigned` column total equals No tester & not self-tested |

**Burndown (sprint page), computed over the filtered set.** Days = every calendar day from `sprint.startDate` to `sprint.endDate`, inclusive (N days). For a ticket, `addDay` = day index of `addedDate` (null or on/before the start = 0; after the end = N-1) and `doneDay` = day index of `doneDate` for Done tickets (before the start = 0; after the end = outside the chart, ignored), raised to at least `addDay`. For day `i` (0-based): `scope(i)` = sum of `points` (missing = 0) of tickets with `addDay <= i`; `done(i)` = sum of `points` of Done tickets with `doneDay <= i`; `remaining(i) = scope(i) - done(i)` for days up to today, where today = `refreshedAt` clamped to the sprint (no value before the start; the last day if after the end); `null` after today. `ideal(i) = scope(0) * (1 - i / (N - 1))` (the starting scope falls linearly to 0 on the last day; a one-day sprint has ideal 0). Done tickets with a null or invalid `doneDate` are not subtracted and are counted for the footnote. When `sprint.removed` is present, each removed entry (after the sprint filters) is also in scope from its `addDay` (absent `addedDate` = day 0) until its `removeDay` (day index of `removedDate`: before the start = 0, after the end = N-1, never earlier than `addDay`), when its points leave the scope; it is never counted as done. Without `sprint.removed`, removed tickets are not modelled (no data). Re-estimates are never modelled. `total` (the y-axis top) is the largest scope on any day; this matters when removals make a historical day's scope higher than the final day's scope. The y axis tops out at `total`. The removal markers sit on the `removeDay`. The mid-sprint markers use the same set and the same threshold as the KPI, one marker per date, placed on the day of `addedDate` (clamped to the last day).

**Overlap rule.** A ticket's points are one number for the whole ticket (dev + test effort). The full points count for its assignee **and** for its tester. The assignee view and the tester view therefore overlap by design: do not add them together. The sprint total counts each ticket once.

**Per-view invariant** (useful for checks): every ticket has exactly one assignee group and exactly one tester group (`Self-tested` and `Unassigned` included). So with no filter active, the totals of the status tile, the type tile and the matrix all equal the sprint totals. With filters, the same holds inside any tile whose own dimension is unselected.

**Backlog metrics (over the relevant set):**

| Metric | Definition |
|---|---|
| Backlog tickets | count of tickets |
| Estimated story points | sum of `points`, missing = 0 |
| DoR / Priority / Type distribution | count per dimension value (§ table above) |
| Days in status distribution | count per Age bucket |
| Median days | median of non-null `days` (average of the two middle values for an even count); `—` when none |
| Needing refinement | `dor` is `Weak` or `Missing` (`DECISIONS.md`, D12) |
| Needs splitting | count of tickets with a non-null `needsSplitting` |
| Readiness x priority | cell = count of tickets with that priority and that DoR value |

Priority order for display: `Highest`, `High`, `Medium`, `Low`, `Lowest`, then any other value, then `—`. DoR order: `Well-Formed`, `Ready`, `Weak`, `Missing`, `N/A (Epic)`, then any other value, then `—`. Colours: Well-Formed and Ready green, Weak yellow, Missing red, the rest gray. Needing refinement stays Weak + Missing.

## 7. Searching (both pages, R001-19)

- **Normalising.** Query and field values are lower-cased, accents removed (Unicode NFD without combining marks) and spaces collapsed. Words split on spaces and punctuation but keep `.`, `-` and `/` inside a word (`4.46.1.0`, `well-formed`, `n/a`, `APP-2970`).
- **Whole phrases first.** Sprint: `in review` → `status` = `In Review`; `in progress` → `status` = `In Progress`; `dev to test`, `qa to test`, `same person` → the Self-tested value (§6, self-tested rule); `self-tested` → any of the three. Backlog: `well-formed` → `dor` = `Well-Formed`. Each phrase is matched only against its own field.
- **Other words**, AND across words, each matching at least one allowed field. Sprint fields: `ticket` (anywhere: partial key), `summary`, `status`, the Self-tested value, `parent` (a word start, or inside a Jira key in it), `fixVersion`, `owner`, `tester` (not `Unassigned`) — all others by the start of a word. Backlog fields: `ticket` (anywhere), `summary`, `dor`, `epic` (a word start, or inside a Jira key in it). No other field is searched (sprint: not `lastSyncUpdate`, `linkedWorkItems`, `type`, `points`, `blocker`; backlog: not `type`, `priority`, `risk`, `needsSplitting`, `cluster`, `quickCheck`).
- **Order.** When a query word is a full key (`app-2970`) or a key number (`2970`), the ticket with that key comes first in the table; the rest keep their order.
- The search is AND with every other filter, applies to every tile on its page, and is kept in the URL as `q`. It never changes the data.

## 7a. Jira links (display only)

The data files carry no URLs. The UI builds links when it displays a cell, from keys already in the data:

- **Key pattern:** `[A-Z][A-Z0-9]+-[0-9]+` as a whole word (regular expression `\b[A-Z][A-Z0-9]+-[0-9]+\b`). Lower-case text, `ABC-` without digits, or a key glued to other letters is not a key.
- **URL:** `https://mysnaplogic.atlassian.net/browse/` + the key (URL-encoded). The base address is one constant in `dashboard.js`.
- **Columns:** `ticket` (whole value, linked only if it matches the pattern exactly, otherwise shown as plain text); `parent` and `linkedWorkItems` (sprint); `epic` and `cluster` (backlog): every key inside the value is linked and the surrounding text, including separators and the dash, is shown unchanged. No other field is linked.
- **Safety:** link text and targets come only from regex matches, so other characters in the data can never become markup or a different address. Text is always built as text nodes.
- The exporter, the JSON files, the schema and the fixture are unchanged by this feature.

## 8. Things the UI must not do

- Read Excel, call Jira, or call any network endpoint.
- Write or modify any file, or send data anywhere.
- Re-rank the backlog. The sheet order is the ranking.
- Remap or drop unknown statuses or DoR values.
